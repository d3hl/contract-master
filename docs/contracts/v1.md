# Portable contracts v1

No prior contracts existed in this empty repository. `contracts/v1/` is the single
baseline, not a second protocol alongside Orca. Future compatible additions stay
in this version with migrations; incompatible semantics require a new version.
Orca Task/Dispatch IDs are authority references, not replacements for these payloads.

All payloads are UTF-8 JSON. Schemas use JSON Schema 2020-12. Runtime validation
implements exactly the subset used here (object/array/scalar types, required fields,
constants/enums, patterns, minima and uniqueness); it is not a general validator.
Unknown fields and versions fail closed. The schemas are the source of field rules.
A schema keyword outside that subset is an error at load time, never ignored.
Patterns must be anchored (`^…$`) so standard validators agree with ours. One
deliberate difference: `minLength` ignores surrounding whitespace. CI cross-checks
the payload fixtures with the `jsonschema` package (a test-only dependency).
`task.plan` embeds a copy of the plan schema; a test keeps the two identical.

| Contract | Required meaning |
|---|---|
| issue | Current provider identity/project, repository/base, executable/tracking kind, goal, scope, acceptance, check IDs, dependency identities, status and optional `repo_labels` (Linear `repo:` labels) |
| task | Identity, repository/base, phase, plan/revision, context commit/digest/location, scope, acceptance, checks, attempt and corrections |
| plan | Claude author, bounded steps, documents explicitly read, code investigation, latest HANDOFF read/verified absence, Context7 sources |
| implementation-result | Exact output commit, attempt/plan/context binding, summary, check outcomes, concerns, artifacts, changed files |
| verification-result | Codex author, exact reviewed commit and bindings, each acceptance criterion with evidence, independent check outcomes, verdict, actionable corrections, actual diff evidence |
| completion | Claude author, accepted and merged commit, Codex reviewer/merger, provider/correspondence/acceptance evidence, checks on merged commit; requires separately recorded provider confirmation |
| handoff | Phase, owner, workspace/branch/commit, completed work, verification, blockers, exact next action |
| runner | Portable role, mode, capability inventory, evidence, Orca client adapter identity, optional paired Orca `environment`, enabled flag |

Required runner capabilities: read files, edit files, execute commands, use Git,
return structured results. A chat-only HTTP endpoint is insufficient. Select a
client only after proving these capabilities on the execution host. Do not assume
an Orca agent called `deepseek` exists. The configured `deepseek-portable` runner has passed a
[real OpenCode capability probe](../operations/runner-verification.md) and remains
disabled for production. Its client-specific model configuration is documented
in that report; the portable contract does not require OpenCode for other runners.

The task envelope includes plan contents and previous verification corrections.
A runner must explicitly load `context.path`, validate digest/source, load target
entry points, and report the requested commit. A runner without direct Context7
receives resolved, versioned excerpts and links from the manager/coordinator.
Do not put secrets or confidential issue/code content in Context7 queries.

Use CLI `--help` for trusted coordinator operations. Worker JSON is validated by
`implementation`, never evaluated as shell. Required checks are registry IDs; only
the trusted registry provides argv and timeouts. Codex can use
`contract_master.evidence.inspect_checkout` in a clean verification checkout to
collect the actual diff and run the checks. Review the diff and criterion evidence
before submitting `verify`; that helper does not decide semantic acceptance.

`open-pr TASK TOKEN [--live]` pushes the output commit to the task branch and opens
or reuses its PR as the PR-opening App; it records `pull_request` (`number`, `url`,
`opened_by`). `codex-merge TASK TOKEN [--live]` checks, approves and merges as the
Codex App and records `merge_steps` (`check`, `approved`, `merged`, or `stopped`),
then runs `confirm-merge`. Without `--live` both only report intended steps and
blockers. `--live` requires `automation_enabled`, `merge_gate_audited` and complete
`github_apps` (`pr`, `merge`: `slug`, `app_id`, `installation_id`, `key_reference`).

For completion use `confirm-merge TASK TOKEN PR_URL` first (`codex-merge` runs it). The read-only GitHub
adapter validates the registered repo, exact PR head, actual merge, the latest
approval from the registered Codex `merge_identity` at that head, the Codex merger,
and that no human's latest review requests changes. Other providers need a reviewed
adapter. `complete` then requires matching provider facts plus Claude correspondence
and merged-commit test evidence. Neither workers nor issue text select provider code.

`inspect-checkout TASK WORKSPACE OUTPUT_SHA` exposes independent Git diff/check
collection through the CLI. Use a clean verification checkout with the recorded
output SHA. The task snapshots trusted check argv and policy digest, so editing
current registry commands cannot change a retry. This command collects evidence;
Codex still decides whether each acceptance criterion is satisfied during
verification; Claude reconfirms acceptance on the merged commit.
